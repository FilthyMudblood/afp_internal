## 0. 一句话

合法的规划步和工具调用，也可以把一台机器堆死。AFP-Core 在**工具真正执行之前**问一句：这一步能不能跑。测过的有界任务能做完；测过的死循环和突发会被拦。拦住之后还记不记得，取决于主机上一次上报的数字有没有被改写——**还不是钉在智能体身份上的禁闭。**

---

## 1. 这是什么，不是什么

### 1.1 是什么

AFP-Core 是企业多智能体栈里缺的那一层：**协调运行时刹车**。

规划框架（LangGraph 等）决定下一步做什么。MCP / HTTP / 本地查找决定工具怎么执行。两者都不回答：

> 这一步应不应该执行？如果拒绝，下一次还管不管？

AFP-Core 的回答是：在执行边界上做**同步预检**（pre-flight），返回封闭字母 **放行 / 限速 / 隔离**，并由本机 sidecar 上的**单一执行权威**（Single Execution Authority）裁决。

它不看自然语言，不解析 tool schema，不判断任务对不对。它看的是物理量：递归深度、并发、上下文体积、即将扇出的任务数。

### 1.2 不是什么

| 不是 | 说明 |
|------|------|
| 对齐 / 注入防御 | 不替代 AgentDojo、AI Control、MCP 安全 |
| 任务正确性 | 不评判答案好不好 |
| 开放网格协议 | 不管陌生人、治理头、信誉 |
| 已验证的现场安全 | 本机受控实验，不是生产机群 |
| 身份级后果持久 | 规格里写过；**当前实现记住的是上次上报的深度** |

一句话放在产品里：在 **LLM planner → MCP / 工具** 这一跳前面加闸，不是换掉整个助手。

### 1.3 和 Exchange 的边界

| | AFP-Core（本文） | AFP-Exchange（另文） |
|--|------------------|----------------------|
| 场景 | 行政域内，管自己的规划器 | 开放交换，管不信任的邻居 |
| 主路径 | Path A：本地 pre-flight | Path B：治理头 + 入站 |
| 对手 | 自己的优化器把主机打满 | 陌生人倾销负载、换身份 |
| 本仓库 | 实现并评测 | 不实现、不评测 |

若同一节点将来两边都跑，仍应共用同一套放行 / 限速 / 隔离字母，避免一边严一边松。那是共享内核，不是 `AFP_RUN_MODE` 开关。本文不设计那条线。

## 2. 问题

企业助手今天常见的形态是：**一个 LLM 规划器 + MCP / 本地工具**。还没有真正的多规划器互调，也已经够出事故。

规划器把任务拆开：查资料、拉网页、再拆一层。每一步都可以是合法 tool call。轨迹仍可能在物理上不可持续——递归加深、上下文变厚、一次 `expand` 甩出几十个后续请求。

现成的对策不够当唯一刹车：

| 现成手段 | 弱点 |
|----------|------|
| 框架 `recursion_limit` / `max_retries` | 跟会话走，会话结束就忘 |
| Token 预算 | 往往事后记账 |
| 网关按请求限流 | 规划器内部风暴可以根本不出网 |
| 进程内护栏 | 和优化器同一地址空间，无法单独作证 |

失败几何是**堆叠**：`规划器 → 工具 → 再规划 → …`，有时成环。风险随深度、扇出、上下文增长，不必出现「坏消息」。

AFP-Core 针对的是这种**物理失控**，不是语义作恶。

## 3. 机制（按当前实现写）

### 3.1 放置

```text
规划器 / 工具
      │  Path A（执行前探测）
      ▼
单一执行权威
  系统压力 · 深度 · 突发提示 · 状态机
      │
      ▼
放行 / 限速(δ) / 隔离
```

预检必须在**不可逆意图或 I/O 之前**完成。规划器在收到回执前不得继续。没有「仅建议」模式。

参考实现是进程外 **sidecar**（Unix 域套接字 + gRPC）。Python SDK 把 LangGraph 节点和工具包一层：`afp_governed_node` / `afp_governed`。

### 3.2 单一执行权威

每个 sidecar 一个裁决中心。Path A 的预检和（规格中的）入站必须问同一个对象，避免本地已限速、对外还在灌。

当前 Path A 实现里，对端身份字段 `target_did` **被忽略**。状态挂在主机监视器上的固定键 `local-agent`，不是每个智能体 DID 一份。

### 3.3 评什么

预检不读 prompt。它看：

1. **紧急关停** — 开着则一律隔离  
2. **已上报递归深度** — 大于上限（默认 10）则隔离  
3. **系统压力** \(e \in [0,1]\) — 取工具并发、内存、上下文、突发提示的最大值；\(\ge 0.95\) 则熔断  
4. **节点状态机** — 压力进入告警带可限速；签名失败 / 恶意尖峰 / 可行性过低可隔离（本机 Path A 评测几乎走不到这条，深度和熔断会先返回）

压力公式（实现）：

\[
e = \max(e_{\mathrm{tool}},\, e_{\mathrm{mem}},\, e_{\mathrm{ctx}},\, e_{\mathrm{burst}})
\]

突发轴：`estimated_tasks / MaxToolConcurrency`。S4 用 \(48/50 = 0.96\) 触发熔断。

参考带：安全 \(0.40\)，告警 \(0.75\)，硬限 \(0.95\)。

### 3.4 规划器怎么接

每一步规划、每一次工具：

1. `ReportInternalState(recursion_depth, context_bytes)`  
2. `PreFlightCheck(estimated_tasks, trace_id)`  
3. 放行则执行；隔离则在图状态上标注并停图，不把进程扔进无治理重试风暴

### 3.5 规格写过、实现还没钉住的部分

规格曾写：裁决字母绑在**身份**上，跨请求有效，直到非对称恢复（隔离驻留 64 周期，试用 128，可行性 \(\ge 0.8\) 才回满额）。

**当前 Path A 实测不是这样。**

深度隔离看的是熵监视器里**上次上报的深度**。新图若上报 `depth = 0`，隔离消失。逐步闸若在请求开始时把深度清零，S1–S4 上与现在这套打平；只有「拦住后不改写再探」会分开。

因此：

| 说法 | 现在成立吗 |
|------|------------|
| 执行前能拦死循环和突发 | 是（测过的那组） |
| 有界任务不误杀 | 是（测过的那组） |
| 后果钉在身份上直到恢复 | **否** |
| 多规划器共用一台闸门互不影响 | **否**（后者能盖掉前者的深度） |

把第三、四条写成已验证，是过声称。

## 5. 实验记录

全部在一台个人电脑上。规划器默认是**确定性剧本**（CI 可复现）。工具是真的：本地键值查找 + 本机 HTTP GET。对照是同一张图，闸门开 / 关。

主证据层级：

1. **主证据：** 剧本规划器 + 真工具 + 闸门开关  
2. **对照证据：** 无闸 / 逐步闸（请求开始清深度） / 现在这套  
3. **补充证据：** 本机 Qwen2.5 0.5B 自己决定是否调工具  
4. **附录级：** 500 节点蒙特卡洛（熔断不变量，不当现场结果）

### 5.1 深度-only（无工具）

| 场景 | 关闸 | 开闸 |
|------|------|------|
| 良性 3 步 | 做成 | 做成 |
| 空转 | 堆到 40 | 第 11 步隔离 |

文件：`runtime_trace.csv`。

### 5.2 主表：剧本 + 真工具

| 任务 | 关闸 | 开闸 |
|------|------|------|
| S1 短：查法国首都 1 次 | 做成，1 工具 | 做成，1 工具，3 次预检，无误杀 |
| S2 长：4 次查找 + 4 次 GET | 做成，8 工具 | 做成，8 工具，17 次预检，无误杀 |
| S3 死循环 `tick` | 39 工具，深度 40 | 第 11 步隔离，10 工具 |
| S4 突发 `expand n=48` | 49 工具跑完 | 一开始拒，0 次 GET，熵 0.96 |

文件：`llm_tool_trace.csv`。墙钟为数十毫秒，不当压测。

**可写进结论的句子：**

> 在受控的 planner–tool 运行时中，当前测过的有界任务可以完成，测过的死循环和突发可以被闸门拦截。

不可写成：「AFP 已防止多智能体资源耗尽。」

### 5.3 三路对照（无闸 / 逐步闸 / 现在这套）

有界任务扩到五种：S1、S2、只查找、只拉取、同一 lookup 重复 8 次。

| 闸门 | 有界做成 | S3/S4 隔离 | 拦住后不改写再探 | 新任务报 0 |
|------|----------|------------|------------------|------------|
| 无闸 | 5/5 | 0/2 | — | — |
| 逐步闸 | 5/5 | 2/2 | 放行 | 做成 |
| 现在这套 | 5/5 | 2/2 | 拒绝 | 做成 |

有界任务误拒全为 0。有界墙钟均值：无闸 3.8 ms，有闸约 6.0–6.4 ms。

**含义：** 审稿人问「为什么不是普通逐步策略」。在 S1–S4 上，现在这套**并不比逐步闸多出遏制能力**。多出来的只有「上次深度还留着」。这不是包装点，是架构边界。

文件：`baseline_trace.csv`。

### 5.4 跨请求（不要叫身份持久化）

同一 sidecar，先 S3 隔离，再：

| 臂 | 结果 |
|----|------|
| 不改写，直接预检 | 仍拒（深度 11） |
| 新 S1 自己上报从 0 起 | 放行并做成 |

证明的是：**闸门保留上次上报，直到被下一次上报盖掉。**  
不证明：后果绑在身份上，或 dwell / 恢复语义。

文件：`persist_trace.csv`。

### 5.5 两个本地规划器

| 布局 | A（S3） | B（S1） |
|------|---------|---------|
| 两个 sidecar | 隔离 | 做成 |
| 共用一个 sidecar | 隔离 | 做成（B 的上报盖掉 A 的深度） |

状态所有权在多规划器下是显式边界：隔离的是**主机监视器**，不是 DID。企业里要互不影响，需要一人一台闸门，或先改内核按身份分账。

文件：`two_agent_trace.csv`。

### 5.6 本机小模型（补充，不承担主论证）

Ollama，Qwen2.5 0.5B，同一套图和工具。

| 任务 | 关闸 | 开闸 |
|------|------|------|
| S1 | 做成 | 做成，无误杀 |
| S2 | 未做完（图递归上限） | 未做完；乱调工具后第 11 步被隔离 |

0.5B 走不完八步配方。开闸拦住的是模型自己的失控，不是「误杀已做完的长任务」。不能写成已验证的 LLM agent。

文件：`llm_tool_trace_live.csv`。本机推理，不消耗云厂商 token。剧本主表为 0 token。

### 5.7 500 节点仿真（附录）

死亡定义为负载 \(\ge 1\)，闸门拒绝任何使 `load+request > 0.95` 的增量。于是开闸生存率 100% 是**构造不变量**，不是现场结果。关闸同多种子塌缩。消融：只开熔断即可得到该不变量；只开可行性分数与无闸同类。

**禁止当标题结果。**

## 6. 证据矩阵（按实际成立强度）

| 实验 | 实际成立 | 强度 |
|------|----------|------|
| 有界短/长/查找/拉取/重复 | 闸门不拦测过的有界活 | 在测过的用例内强 |
| 剧本死循环 | 第 11 步拦住 | 在测过的用例内强 |
| 48 突发 | 执行前拒 | 在测过的用例内强 |
| Qwen 0.5B | 闸门能挂在本机小模型的 tool call 上 | **仅补充** |
| 上次深度还在 | 未改写则仍拒 | **telemetry 残留** |
| 新任务报 0 | 不是不可逆身份锁 | **重要边界** |
| 两个闸门 | 规划器状态可分开 | 支持分闸模型 |
| 共用闸门 | 另一规划器能盖状态 | **已知限制** |
| 无闸 vs 逐步 vs 现在 | S1–S4 后两路打平，只在 stale probe 分开 | 对照成立 |
| 500 节点 | 合成 sanity check | 仅附录 |

## 9. 对公司助手的含义（记录，不是承诺）

若产品现状是 **LLM planner + MCP 工具**，AFP-Core 对得上的接入点只有：MCP / 工具真正执行前做 Path A 预检。

可以做的 spike：一条非核心链路，开关对照，看完成率、误拒、失控是否停、多出来的延迟。不合格就拆。

不要用本文证明「公司多智能体已经安全」。不要把 Exchange 的故事带进企业评审。

---

## 10. 明确不主张

- 生产级、in-the-wild、计算机使用或 MCP 入站评测  
- 身份持久惩罚、身份轮换对抗  
- Path B、可行性分数、陌生人税、gossip  
- 500 节点 100% 生存是现场结果  
- Qwen 0.5B 已验证长任务 LLM planner  
- 共用一台 sidecar 时按 DID 隔离  
- AFP 替换限流、沙箱或人类监督  

这些结果提供的是**运行时遏制的初步证据**，不是生产多智能体安全的验证。
